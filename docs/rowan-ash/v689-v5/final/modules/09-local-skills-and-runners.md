# Module 09 - Local skills, runners and catalogue use

The phase creates twenty local skills and ten paired runner interfaces. Ten skills and five runners belong to x1, and ten skills and five runners belong to x2. The names describe family capabilities without embedding Rowan's name or a release number. Each local skill points to the relevant paired interface and to an explicit frozen example. The catalogue records its repository-relative path, current byte hash, declared trigger, owner scope, rollback and protected gates. Use the path and hash when resolving a capability; a familiar name alone is not a byte-identity guarantee.

The first five runners cover simplex faces and orientation; boundary composition; graph components and cycle rank; Euler characteristic and Betti numbers; and chain cycle and boundary membership. The next five cover gradients and Stokes pairings; adjoints and weighted Laplacians; Dirichlet solutions and energy; gauge shifts and harmonic dimension; and provenance with authority reservations. A pair is an interface boundary. Supplying an otherwise valid operation to the wrong paired runner returns E_RUNNER_SCOPE rather than silently routing it somewhere else.

The shared x1 module implements the finite graph and simplicial helpers. The shared x2 module imports those frozen helpers and adds the second tranche. The CLI module supplies strict JSON parsing, duplicate-key refusal, input-size admission and fresh-file output behavior. These implementation modules are named separately from the ten user-facing paired runners. The portfolio does not multiply the number of capabilities merely because the same helper is imported by several interfaces. The package and interpretation scripts are evidence harnesses, not additional independent scientific systems.

The main request envelope has exactly op, payload and synthetic. The public path expects synthetic to be true and the payload fields to match the selected operation. A false synthetic declaration, wrong payload type, unknown operation or unexpected field gets a distinct typed refusal. The CLI can read a UTF-8 file supplied by the caller or standard input. An optional output path is opened as a new file, so an existing result is not silently overwritten. These interfaces make their small task predictable without making a universal claim about every possible use of graph mathematics.

Each of the twenty skill entrypoints passed the official Skill Creator frontmatter validator. Each was also associated with an observed accepting example, and each runner was exercised with positive and adverse payloads. Forty initial CLI smokes covered the twenty operations. Ten additional new probes checked operation-pair refusal across the current x1 and x2 interfaces. Those extra probes are useful evidence for the interface boundary; they do not add proposal novelty or turn a rejected subject into a completed requested action.

Skill validation has a limited meaning. Correct YAML, a valid name and a reachable example do not prove that a skill gives good advice in every future setting. The operation notes therefore carry the important assumptions: orientation must survive normalization, isolated vertices remain part of the graph, rational homology omits torsion, positive weights support the energy argument, and an unconstrained component makes a Dirichlet solution nonunique. A future request outside those assumptions should receive a new scoped design rather than a mechanical application of the existing skill.

These skills remain local to the Rowan phase. No global promotion or shared skill overwrite was performed. The current workflow permits selective promotion, and this phase records the local evidence needed to assess one later. A successor can reuse a qualified local skill immediately where the task and authority match, or make an additive local adaptation in its own lane. A global promotion should additionally check namespace collisions, callers, byte parity, environment expectations and rollback. Never treat a predecessor's name match as permission to overwrite a shared capability.

The final catalogue is the phase-local contribution to the family meta-tool system. It is linked by the compact handoff and by the four-tier cards. That makes the new capabilities discoverable without copying a large catalogue into a chat composer. The source catalogue remains historical evidence. The new catalogue does not claim to have audited all global tools, resolved every old alias or validated another sibling's runtime. Those are separate tasks with their own scopes and evidence requirements.

When a runner fails, retain the exact request, output, expected result, module hash and exit status. Check whether the issue belongs to the mathematics, the public interface, the environment or the receipt reader. This phase had metadata-reader failures after the underlying calculations had already passed. Re-executing the calculations would not repair a line-ending parser. The useful correction was to preserve the original transcript, parse its actual shape and complete the missing metadata layer. That distinction saves work and protects the meaning of the evidence.

For new work, use the local tools as components rather than as a compulsory checklist. Choose the smallest relevant interface, keep the coefficient field and numeric representation explicit, and add a separate witness for any new assumption. A declared package or skill can help organize a phase, but it cannot supply missing measurement data, authority, independent review or deployment approval. The catalogue's evidence labels are intended to make that judgement easier, not to make it automatic.
