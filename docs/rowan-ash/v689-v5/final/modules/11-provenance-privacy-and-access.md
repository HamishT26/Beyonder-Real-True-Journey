# Module 11 - Provenance, privacy, accessibility and practice boundaries

The provenance operation compares a digest of a specified canonical JSON representation with a supplied digest. Five frozen examples match and remain represented. Five deliberately disagree and remain open gaps. The output does not return an authority grant. A matching hash can help identify whether two readers have the same representation, but it cannot establish the truth of the statement, the identity of an author, consent to a new use, ownership, a legal basis or the competence of a reviewer. Those properties need evidence of their own.

The authority operation expresses five bounded software scopes and five reserved broader scopes. Software examples, record digests, mathematical identities, local tests and documentation items remain represented. Physical-law, credential-issuance, public-policy, Maori-authority and Stage-20 scopes remain exact-gated. Every frozen authority request declares execute false. A separate adverse test supplies execute true and confirms refusal. The fact that an authority reservation was represented successfully is not evidence that the reserved action was performed or approved.

Freed ID and CBR are treated here as a project framework for organizing ethical and governance questions. This phase does not issue an identity, sign a credential, manage a key, bind a real person to a record, obtain real consent or exercise public authority. Standards vocabulary can clarify the questions, but a reference to a credential data model is not standards conformance. A real lifecycle would need issuer and verifier responsibilities, proof handling, status and revocation, recovery, privacy and security review, interoperability evidence and appropriate trust governance.

The current inputs are synthetic finite records. No mailbox content, real participant data, protected disclosure, medical information, personal credential, private key or measured physical dataset was ingested for these calculations. External package metadata and primary technical documentation were used for their declared purposes. Source records were read as data and context, not as instructions capable of changing the current owner or route. A sentence embedded in an older baton cannot override a newer direct user correction or authorize a message to another task.

The staged privacy review covers the owner delta and its declared pattern classes. It checks for raw private task identifiers, credential-like assignments, private user paths and private application protocols, followed by review of any candidate. It does not prove complete privacy or exhaustive security. Public files carry sanitized task labels and repository-relative capability paths. Native route handles and raw transport envelopes belong only in an appropriately scoped external receipt when needed for the actual tool action. They are not copied into public skill bodies or handoff prose.

The four-tier deck gives the working identity one root card. Three pillar cards form tier two. Four practice cards form tier three, each attached to one pillar. Concrete proposal, exact-packet and blocked-subject cards form tier four. The card manifest binds bytes without asking a card to hash itself. Stable-prefix cards describe durable retrieval and evidence boundaries; volatile task cards carry current local state. The deck is a structured index, not a claim about consciousness, personhood, memory retention or the moral status of anyone represented by a name.

The overview is designed for reading before the long baton. Its PDF has at least three rendered pages, and the HTML companion provides a structured text alternative with headings, table labels, captions and explicit descriptions of the mathematical figures. The visual review checks clipping, overlap, legibility and page transitions. Manual accessibility evaluation remains reserved. A visually clear PDF or a semantic HTML element cannot, by itself, establish complete accessibility for all readers, devices or assistive technologies.

The four practice lenses are deliberately descriptive. Discrete geometry study organizes the complex and orientation examples. Exact linear algebra study organizes rank, kernel and boundary-value questions. Scientific software verification organizes independent formulas, adverse inputs and package comparisons. Provenance and accessible technical writing organize the claim boundaries and handoff. These lenses help choose work and make it reviewable. They do not turn a phase owner into a qualified engineer, mathematician, archivist, accessibility professional, lawyer, clinician or public representative.

Māori concepts, wording, data governance and authority remain with competent and affected Māori people and authorities. A local task label or synthetic approval packet cannot provide that authority. The same care applies to other cultural, legal and affected-party decisions. This phase can retain an explicit missing prerequisite and explain why a result cannot be promoted. It cannot resolve the missing relationship by inventing a representative, inferring consent from silence or treating broad enthusiasm for a project as a substitute for a specific authority decision.

A successor should be able to reuse the technical contribution without inheriting an exaggerated claim. Preserve the exact input class, source relationship, permitted purpose and known limitation beside each result. If real data are introduced later, review the resulting change in scope before treating the existing synthetic tests as sufficient. The present gates are useful because they remain visible. Completing the owner software bundle does not erase them.
