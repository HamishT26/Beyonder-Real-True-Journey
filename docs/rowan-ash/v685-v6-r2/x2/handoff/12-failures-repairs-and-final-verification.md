# Failures repairs and final verification

A reliable closeout preserves the unsuccessful attempts that shaped the result. This remaster does not present a frictionless history. The retained records include two code defects discovered by focused tests, a mistaken helper-path guess, a Windows decoding failure, a mislabeled byte domain in the planning report, and an incompatible latest package candidate rejected before installation. Their recovery is part of the method evidence. None of the original failed conditions receives success credit merely because a later repair worked.

The first focused code test run contained thirty-two targets. Thirty passed and two failed. One failure showed that Boolean true could satisfy an integer match count. The other showed that a control character could enter a relative seal path. The original scheduler, seal helper, and test definition were copied into the retained-definitions folder before repair. The repaired code was then exercised only against the two failing targets, both of which passed. The resulting review is a dependency-corrected account of thirty-two targets, not a claim that the first full run passed.

The source-path error came from guessing that a global skill contained a helper with a predictable filename. It did not. The recovery was to list the actual package files and use the documented interface rather than invent another path. This is a small but recurring lesson in a large skill bank: a name that looks plausible is not an observed file. The method note records literal discovery as the recurrence guard. A future task should prefer a bounded directory listing or exact registry pointer before constructing a command.

The encoding failure came from Python's default Windows text decoding. Source JSON contained UTF-8 text that could not be decoded with the active cp1252 default. The successful recovery used explicit UTF-8 reads and Python's UTF-8 mode. All new generated evidence writers then used UTF-8 bytes or an explicit newline argument. This is an implementation detail worth preserving because names, Māori text, and other non-ASCII content are normal parts of the project rather than exceptional payloads.

The newline issue requires a more careful explanation. Several planning files were written with Windows CRLF line endings while Git stored normalized LF blobs. The planning validation recorded their checkout-byte hashes but described the domain too broadly as LF. The committed x1 packet was preserved. The x2 correction identifies the affected manifest entries, records their checkout and raw Git blob digests, and confirms normalized-LF parity. The final seal uses raw Git blobs exclusively, so the correction does not require changing or replaying the historical x1 record.

The package compatibility issue was caught during planning rather than as a broken installation. The latest mpmath candidate did not satisfy SymPy's declared interval. The compatible pin was researched and frozen before the transaction. The retained negative is the incompatible condition, not a fabricated failed installer process. This distinction matters because the negative ledger includes both expected rejecting fixtures and actual failed operations. Its total is a count of retained adverse cases with several types, not a count of unexpected crashes.

The method-flow ledger contains twenty-six methods and fifty-two witnesses. Twenty methods summarize the named contract families with supported and adverse evidence. Six methods capture the operational failures or rejected planning conditions and their recoveries. Forty-six witnesses pass and six retain failures. These are same-owner records. The current method validator confirms their schema, backlinks, counts, and privacy boundaries. It does not establish independent reproduction or a universal guarantee that the methods will work in every environment.

Before the final repository closeout, inspect the exact staged allowlist and the current owner delta. The permitted surface is the remaster documentation prefix, the five new core runner paths, and the focused test file. Historical first-run documents remain unchanged. Shared global guidance changes have their own additive update receipts and private backups; they are not hidden mutations in another sibling's worktree. Package environments and raw installation logs remain outside the public repository.

The x2 commit is an immutable execution checkpoint. Final records can summarize it and add navigation, evidence manifests, and the terminal handoff state. The final repository commit must then be pushed and compared against local HEAD, upstream, tracking, and a fresh live remote read. A clean working tree matters because a final receipt should not silently depend on uncommitted changes. A later branch tip does not replace the exact final identifier named by the receipt.

Canonical invocation is the last verification action for the owner delta, not an exploratory test. Complete the ordinary preflight first. Check required receipts and the current hold. Use a distinct external output path for this remaster. The canonical helper creates an exclusive invocation marker and refuses an existing marker or receipt. If it succeeds, do not invoke it again for display, confidence, a newer route lookup, or a later user question. A successful receipt can be read and hashed without being replayed.

A route problem after repository closeout does not require rewriting the repository seal. Keep delivery as a separate external state. For this run that state is prepared not sent, with zero live send and creation calls. If a future released send is accepted but opaque, retain that exact outcome and do not resend. If a route service is unavailable before any call, preserve the unsent gap. Repository equality, canonical success, prepared content, tool acceptance, and recipient acknowledgement are related but distinct facts.

Your future closeout should be understandable to someone who did not watch the commands run. The record should state what changed, why it changed, what was tested, which attempt failed, how the failure was repaired, and what remains unestablished. That is the standard by which this remaster should be assessed. A large quantity of green counts without source, scope, or retained failure history would not meet it.
