# 09 — Tests, witness accounting and retained recovery

The execution record is deliberately more detailed than a single passed total. X1 has fifty main result predicates, fifty input-fixity predicates, one hundred refused malformed subjects and one hundred corresponding passing refusal checks. X2 has the same four denominators. The safe-task count groups each main comparison and its input-fixity check, producing one hundred safe assertions per session. It does not create a second independent set of scientific experiments. The case tables preserve operation, fixture, frozen definition digest, expected output, observed output, predicate result and substantive disposition together.

There are twenty-seven additional x1 tests and seventeen additional x2 tests. They exercise behaviour that the main happy paths alone would not establish: cancelling self-loop arcs, infeasible ordering of a balanced transition multiset, conservation-compatible but unreachable markings, coenabled conflicts, positive commutation, empty sequences, invalid certificates, malformed shapes, token overflow, state-budget overflow, terminal singletons and fairness limitations. The x1 invariant property test contains ninety individual arithmetic assertions. Those assertions are reported as an internal test denominator, not ninety external replications.

The x2 liveness comparison uses a separate fixed-point relation calculation over the hand-declared edge tables. It does not reuse the production engine's generated transition graph as its oracle. This reduces one form of shared implementation dependence and makes the result easier to inspect. Both implementations were still written and run by the same owner. Algorithmic separation is not independent reproduction by another person, organisation or implementation team. That limitation remains explicit in each record.

Local runner validation exercised twenty accepting or refusing calls per session. Curated source validation exercised forty calls across the twenty operation types. Installed validation exercised ten calls across the five public interfaces. Official Skill Creator checks covered the twenty local skills, five curated source skills and five installed skill copies. The installation receipt binds twelve files: five skill documents, five runner interfaces and two support modules. A file-parity result verifies byte equality between specific files; it does not establish a package's complete security or scientific validity.

The owner Method Flow ledger distinguishes failed subjects from passing refusal predicates. It also retains operational failures, including bounded-output problems during intake, a Unicode console failure, the x1 line-ending and output-hash problems, a missing command-session handle in one display projection, and the catalogue search-token mismatch. None of these observations is silently dropped because a later narrow recovery succeeded. Their original success credit stays zero. The corresponding method records describe the concrete trigger, recurrence guard, rollback, protected gates and exact witness references.

The original x1 test-output receipt refers to the pre-normalisation CRLF byte domain. The committed test output uses LF. `x1-addendum/edge-test-output-binding.json` is the controlling correction for that specific pointer. It proves the deterministic normalisation relation and binds the already observed output to its committed bytes. Do not rerun the twenty-seven tests merely to make the old receipt look current. Preserve the original receipt and correction as two stages of the evidence history.

The first catalogue query also remains visible. Its cards stored operation names with underscores, while the shared query runner tokenises search words. The initial query therefore returned zero results. The corrected catalogue uses the existing tokenisation function and returns exactly the local transition-liveness skill and the curated reachability skill. Earlier structural-validation and collision snapshots are retained; corrected files identify the current draft. The repair changed only catalogue metadata and dependent checks. No main contract, unit test or source canonical was replayed.

Method and witness totals are derived from the actual records in `final/method-flow-final.json`, with a separate source baseline and owner delta in `final/method-accounting.json`. They include deliberately malformed subjects and successful guard checks. They must never be described as a tally of independent discoveries, empirical confirmations or perfect tests. Post-canonical publication and routing events belong to later external receipts and are not fabricated inside this repository seal.
