# Module 09 - Local skills, paired runners, and capability selection

Twenty owner-local skills were created, ten in each session. Each has valid frontmatter, a discriminating description, an exact paired runner, a frozen example, assumptions, refusal boundaries, protected gates, and an additive rollback. The official Skill Creator validator passed every entrypoint. Validation of frontmatter and links does not guarantee good advice for every future request.

Ten family-current paired runners expose exactly two operations each. Their shared strict CLI rejects duplicate JSON keys, nonfinite values, oversized input, unexpected fields, false synthetic declarations, wrong payload types, unknown operations, and operations outside the selected pair. Output files are opened only as new files. Forty positive and adverse runner smokes passed across the two sessions. Each rejected subject keeps zero success credit.

The x1 pairs cover grid geometry; interpolation and forward differences; backward and central differences; curvature and quadrature; and error with observed order. The x2 pairs cover Poisson solution with residual; flux with Richardson extrapolation; adaptive splitting with CFL; heat step with energy; and provenance with claim reservation. The shared x1 and x2 cores are implementation dependencies rather than extra user-facing runner counts.

The phase-local catalogue merges the x1 and x2 cards with three shared implementation modules. It records repository-relative source paths, exact SHA-256, evidence state, owner scope, triggers, rollback, protected gates, module allowlists, and the absence of route capability. No global skill installation or shared overwrite occurred. Existing family skills guided the workflow without being recopied as Neris novelty.

A later global promotion should first confirm namespace uniqueness, exact byte parity, caller compatibility, environment assumptions, bounded positive/adverse use, and rollback. An older name remains compatibility evidence when it has callers. Similar filenames are not proof of functional equivalence. A merge should consolidate implementation only, never erase historical receipts, owners, failures, or identities.

Use these local tools only when their exact assumptions fit. A different dimensionality, nonuniform stencil, nonlinear equation, untrusted mesh, real participant, production system, or authority decision needs a newly scoped contract. Availability is not an instruction to run every tool.
