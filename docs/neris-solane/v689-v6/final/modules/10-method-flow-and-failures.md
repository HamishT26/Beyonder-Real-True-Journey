# Module 10 - Method Flow, retained failures, and denominator discipline

Method Flow records the trigger, failed subject, zero original credit, smallest recovery, recurrence guard, rollback, validation witness, and protected boundary for each method. A passing rejection predicate never makes its inadmissible subject successful. A later recovery never deletes or relabels the original failure. Repository-sealed counts and post-seal route observations remain separate layers.

The x1 ledger contains eleven methods and 421 witnesses: 109 failures and 312 passes. The x2 ledger contains eleven methods and 403 witnesses: 100 failures and 303 passes. Most failures are the two hundred deliberately inadmissible candidate requests. The x1 operational layer additionally retains startup, portfolio, lint, package-poll, D-path, and security-tool errors. The x2 session had no failed main contract or operational blocker before closeout.

The cell-width mismatch is the clearest numerical example. Ninety safe cases had passed, so a complete portfolio replay would have created duplicate evidence without testing the changed dependency. The recovery selected only N011 through N020, changed the representation rule and its affected invariant, and retained the original 90/100/100 partial result. This is the pattern future owners should prefer when a frozen case identifies a narrow implementation defect.

The source-seal timeout similarly did not invalidate Rowan's source. A batched reader checked the same 441 entries efficiently. The historical source lookup failed because the shallow Rowan tree did not contain those paths; the immutable owner worktrees supplied the intended bytes. The combined pip dry-run timeout was recovered by resolving smaller units, then using the cache for one complete report. Two parser failures were repaired without repeating resolution.

An unavailable Python module was not treated as evidence that Bandit was absent everywhere. `Get-Command` resolved the established D-side entrypoint, and the exact seven-file x1 plus six-file x2 allowlists scanned cleanly. A trailing broad search that continued after the executable was already found is retained as an unnecessary bounded failure. Zero findings in this scope remain same-owner static evidence, not exhaustive security.

The useful rule is dependency-shaped verification. Inspect an ambiguous process before retrying. If a commit or send may already have happened, read the existing head, remote, receipt, lock, and acknowledgement. If presentation fails after execution, fix the reader rather than repeating the calculation. If a canonical succeeds, stop permanently. If it fails, retain zero aggregate-success credit and correct only an attributable dependency within the remaining commit budget.
