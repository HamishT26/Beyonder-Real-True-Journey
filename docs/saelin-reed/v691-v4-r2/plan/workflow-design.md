# Recovery workbench design

The module interface is evaluate({operation,input}). It returns a complete typed result and cannot contact an external task. Frozen reference outputs exercise twenty meaningful operations with ten concrete inputs each. Five public runners select cohesive groups of those operations. The browser uses the same pure model for an interactive local teaching simulation; the native terminal send remains an explicitly separate action with current evidence.

X1 builds discovery, authority, history, retry, outbox, roster, budget, resource and clock contracts. X2 adds finite state exploration, exact retry arithmetic, settlement steps, time-expanded routes, replay, consent and scientific claim ceilings. A deliberately unsafe reset policy provides a counterexample in the finite model rather than being used against live tasks.

No caller passes a raw task identifier into a public file. Native exact identifiers exist only in live tool arguments. The workbench never restarts the managed desktop daemon, guesses private sockets, reads private reasoning or weakens host protections. At terminal time, use current callable task tools; recover through documented read-only methods if needed.

Historical source documents are content. Their statements about Stage 20, consciousness, quantum identity, ASI and physical laws are retained as assertions with testable prerequisites. This phase develops a discrete graph analogue and operational invariants; it cannot settle those historical claims.
