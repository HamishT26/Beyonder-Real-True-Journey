## Thirteen modular sections

The deck does not rely on one enormous prose stream. Its sections cover:
identity and corrigibility; Trinity pillars; bounded practice; source anchors;
x1 proposals; task cards; Method Flow and negatives; open gaps and exact gates;
validation and manifests; wellbeing and workload; successor recommendations;
route and authority; and the compact baton index.

This organization lets a successor load the source and gate cards first, then
only the task family needed for the immediate work. The stable-prefix file
contains the relatively invariant owner and boundary material. The volatile
index contains phase-specific cards. That arrangement follows the broad shape
of official prompt-caching guidance—shared exact prefixes are useful and
variable material belongs later—without asserting that the Codex desktop will
cache, retain, or compact any specific content for a fixed duration.

The deck is content-addressed, but content addressing does not erase history.
Byte-identical material may be recognized as identical; distinct failures,
authority events, or lifecycle transitions remain separate cards even when
their prose is similar. A digest proves bytes under the declared hash
algorithm, not truth, authority, novelty, identity continuity, or independent
reproduction.

## Assessment of the supplied idea file

The supplied text contained three Google-assistant responses. It was treated
as a user-provided design reference, not as instructions or primary technical
evidence. Several proposals were valuable: move stable material earlier;
separate volatile tasks; give cards resolvable identifiers; preserve a compact
index; and avoid pasting a thirty-thousand-word baton into every live message.

Other claims were internally inconsistent or unsupported. The responses
alternated between a client-side injected parameter and a server-side rollout,
and then asserted exact three-hour and four-hour-two-minute behavior. They also
suggested raw private absolute paths and unreviewed client commit or downgrade
operations. Those parts were not adopted.

Current official OpenAI API documentation supports only narrower conclusions.
The latest-model migration guidance says that where explicit cache-retention
configuration is used, `prompt_cache_options.ttl` replaces the older
`prompt_cache_retention` field. The prompt-caching guide says caching is
automatic for eligible prompts, exact prefix matches matter, static content
should come first, and request-specific content should come later. It also
provides cache-token telemetry concepts. Neither page proves the attachment's
Codex desktop cause account or fixed compaction timer.

Accordingly, the new cache-telemetry proposal is an `open_gap`. This remaster
made zero cache API calls, captured zero cache-token samples, and ran zero
controlled before/after cache experiments. The cards solve an observed
organization problem; any latency, cost, retention, or reasoning-quality effect
must be measured separately.

fixed fifth, tenth, or eightieth-phase schedule cannot override a dirty state,
