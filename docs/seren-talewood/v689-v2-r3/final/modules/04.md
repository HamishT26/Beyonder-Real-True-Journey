# Module 04 Execution scope and the meaning of the workload counts

The workflow freezes definitions before executing each planned tranche. The initial planning commit is separate from x1 implementation, x2 implementation and final closeout. A spontaneous addition needs an explicit definition before its execution, with any ordering defect disclosed. The weighted reviewer was specified in the startup discussion, while its standalone definition file was written after implementation and before execution. The later scientific experiment and compound-composer files were defined before their execution; the compound was also defined before its implementation.

The user authorized suitable safe, candidate and exact work. This removes a generic approval wait for concrete actions in scope. It does not make an invalid proof true, supply a participant's consent, authorize an unspecified destructive target or convert a synthetic record into a real-world credential. Keep authorization and evidence in separate fields. The thirty blocked subjects remain unexecuted reservations.

There are two hundred inherited source refinements. Each transformation turns an exact source contract into typed path/value nodes, reconstructs it and checks its canonical digest. A list index, a string key, an integer, a Boolean, null and an empty container remain distinct. The transformation preserves the original record and adds a portable view. These are real record refinements, not two hundred operating-system cleanups and not a second execution of the inherited model.

Each candidate procedure adds an undeclared execute field to a complete request. The evaluator must return E_FIELDS before calling the model operation. The invalid subject retains zero success credit even though the rejection check passes. The safe catalogue also includes deliberately invalid domain inputs. In each session, sixty model subjects are accepted and forty are refused according to their frozen expectations. Thus a passing software check and a successful underlying subject are deliberately separate concepts.

The fifty original exact packets covered thirteen package additions, twenty skills, ten planned runners, six shared integration groups and the Eiren terminal action. The spontaneous combined skill and runner add packets fifty-one and fifty-two. The extra weighted route reviewer is recorded as a safe addition. Fifty-one of the fifty-two exact actions are complete before the live terminal handoff. The actual native action is recorded only when it happens, never inferred from this arithmetic.

The owner main branch is reused, following Hamish's preference. The base r2 tree stays unchanged, and all new r3 files are additive. Both tracked and materialized file counts must remain below two thousand. Package environments, wheels, caches, long handoff backups and validation materializations live on D outside the Git tree. Essential skill discovery files and explicitly requested memory metadata are the C-drive exceptions. Do not remove another owner's files or alter sibling model settings as a cleanup shortcut.

File counts, task counts, methods, tests, records and proposals use separate denominators. A repeated interface confirmation does not create another proposal. A global byte-parity check proves the same code was copied; it does not establish independent reproduction. A numbered packet that remains blocked has no execution credit. The final checklist and count reconciliation are intended to make these distinctions easy to audit without loading every artifact at once.
