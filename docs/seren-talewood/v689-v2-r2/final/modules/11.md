## Module 11: Four-tier cards and selective context loading

The combined deck contains seven hundred content-addressed cards. The x2 base has 697 cards: one working identity anchor, three pillar cards, four practice cards and the task, proposal, packet, method and tool details. A later x2 formatting-method extension adds one card without altering that base. The final extension adds two cards, one for the isolated final fixture method and one for the prepared terminal route. Every extension has its own index and hashes. The final total does not imply all future owners have loaded the deck.

The hierarchy starts with the owner working identity at tier one. GMUT Mind, THOS Body and Freed ID/CBR Heart are tier two. The four practice lenses are tier three. Specific work appears at tier four, linked to the relevant immediate parent. This order makes the active context interpretable: a task's scope can be traced through its practice and pillar to the owner record. The validators reject missing parents and inappropriate tier jumps. Content addressing binds each card's payload, excluding only its own card_id field.

Stable-prefix and volatile-index files separate enduring orientation from the changing task records. They are an organizational choice, not a measured prompt-cache or retention result. To load a task, select its card and every required ancestor. Unloaded cards remain on disk, and selecting a subset does not delete or supersede them. A later correction adds a new record with provenance rather than changing the meaning of an old hash. Repeating the same card or including it in both a full baton and a module file creates no additional evidence credit.

The full baton has thirteen modules, with the same modules available as separate Markdown files under final/modules. Its module index supplies titles, hashes and word counts. Read module one for current authority, module two for routing, module three for limits, and then only the source, contract, tool or pillar modules needed for the next concrete action. Full contract JSON is included where it helps a successor reproduce the precise input and expected envelope. Narrative summaries provide interpretation without replacing the structured records.

Before a task handoff, place the long baton and receipts in the existing D-drive bank and owner worktree. The live message should remain short and carry the exact local pointer, the final head, the canonical outcome and the next owner/phase. A public repository document uses relative paths and hashes; a locally delivered message may contain the D-drive location explicitly requested by Hamish. Raw private task identifiers never belong in the published baton. The current native-route gap is a transport limitation, not a reason to manufacture an alternative task endpoint.

Operational wellbeing records describe bounded workload choices, preserved source evidence, concise entrypoints and pausable module boundaries. They do not diagnose emotions, fatigue, personhood or continuity. The warm working language can remain while the evidence record stays literal. No claim is made that all thirty owners have experienced or internalized a shared update merely because a global file exists; each future run must select and read its current entrypoints.
