# Cross-platform continuation and numbered-agent onboarding

**Documentation proposal — 23 November 2026, Pacific/Auckland**

This note extends the [22 November workflow note](CD30-WORKFLOW-20261122.md). It describes how an existing programme can resume across ChatGPT, Dots and an additional CLI platform while preserving the meaning of earlier evidence. It introduces three proposed task lanes and a way to make their work reviewable. It does not add a runtime adapter, deploy an agent service or claim that a proposed task has executed.

## Resume from evidence

A continuation should identify the last accepted checkpoint, the current instruction and the smallest next scope. A new instruction can authorize new work without changing the result of an earlier attempt. An earlier timeout remains a timeout. A source review remains a source review. An unrun case remains unrun until a later, separately identified execution supplies evidence for that case.

The current coordination design preserves several distinct records: the original observation, its later interpretation, a correction when required, and the evidence supporting a new decision. It does not overwrite an unfavorable first result with a later successful one. Keeping these records separate makes it possible to distinguish a repaired implementation from a test that was merely renamed or omitted.

Execution prerequisites are specific to a target. An interpreter label in a plan does not establish that an executable exists on a connected machine. A supervisor design does not establish that its deadline, output bound or cleanup behavior has been enforced. A file manifest establishes agreement with recorded bytes; it does not itself establish who produced those bytes or authorize their execution.

For a reproduction, the evidence should bind the source revision, input version, resolved runtime, supervisor revision, invocation, resource admission, output and final process state. Differences that matter to the claim should be explicit. Requirements should not be silently relaxed simply because a different platform is easier to reach.

## Three proposed work lanes

The participant labels below are routing labels for existing user-created sessions. They are not independently verified model identifiers. Personal names, roles, hopes and gender choices are deferred. Suggested learning subjects are a work plan, not a claim that an assistant has acquired a professional qualification.

| Participant | Initial task lane | First useful outcome |
| --- | --- | --- |
| Numbered participant 1 | Runtime identity and supervision | A dated, reviewable mapping from one existing runtime to its actual supervisor, or a precise statement of the missing evidence. |
| Numbered participant 2 | Repository intake and artifact custody | An actual repository/branch and destination inventory, with additive-copy and rollback rules that preserve existing changes. |
| Numbered participant 3 | Portable identity, memory and interface contracts | A proposed distinction between public identity metadata, credentials, permissions and memory provenance, with explicit correction and export behavior. |

The prepared internal backlog contains thirty work items for each lane. Each item has an x1 preparation step and an x2 evaluation or execution step. Thus the plan contains ninety work items and one hundred eighty planned stage actions. Those are planning counts. They are not completed-project, execution, independent-review or adoption counts. This public note does not publish the operational task records.

An item should have a stable ID, bounded purpose, inputs, dependencies, acceptance conditions and expected evidence. Its actual evidence references begin empty. A blocked item should name a concrete missing input rather than automatically producing repeated attempts. A successful document check may complete that document task while leaving the larger runtime or deployment project open.

## Connect existing sessions without changing their identity

Remote access, a running model session and the ability to deliver a message are distinct capabilities. A service can be reachable while no desired session is available through it. An account can be signed in while no local instance is connected. A CLI executable can be installed while its remote-control daemon is not registered. None of these observations should be substituted for another.

The official [Antigravity remote-control documentation](https://antigravity.google/docs/remote-control/?tab=cli) distinguishes an interactive session's remote-control connection from a headless daemon. Coordination should preserve the existing conversation selected by the user, verify the recipient visible in the interface and avoid creating a replacement merely because the expected session is missing.

Before sending, the coordinator checks the current conversation and any existing draft. A saved mailbox body, a sent pointer, a recipient's actual reading, an acknowledgment and the completed assignment are separate events. An uncertain send requires destination reconciliation before a retry. This reduces duplicate work and protects an unfinished user draft.

The proposed support mechanism also distinguishes an active task, a genuine pause and a user handoff. A supported future check should name the exact pause, its stop conditions and a stable delivery marker. It should not wake an already active conversation, overwrite a draft or imply continuous background operation when no such mechanism has been established.

## Identifiers and encryption have different jobs

Readable names and participant profiles support organization, continuity and understandable audit records. They do not create cryptographic secrecy. A long or meaningful name must not become an encryption key, authentication secret or bearer capability merely because it looks distinctive.

The proposed identity architecture separates a stable public identifier from the credential that authenticates it, the policy that authorizes an operation and the cryptographic key that protects a particular data domain. A display name may change while the stable identifier and correction history remain intact. Key rotation should not require pretending that the participant or its entire memory history has become a new entity.

[RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html) provides UUID formats and cautions against treating knowledge of an identifier as access authority. Random identifiers can reduce accidental collisions and improve routing, but their possession must not grant access to a private memory bank. The proposed design therefore requires authenticated binding between a principal and its credentials, plus operation-specific authorization.

[NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final) specifies authenticated encryption through GCM and authentication through GMAC, including the requirements that make their use valid. [NIST SP 800-57 Part 1](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final) addresses key management, while [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final) describes explicit authentication and authorization in a zero-trust architecture. These are design references. This documentation does not implement encryption, issue credentials or attest a production security boundary.

An implementation review should examine key generation, storage, separation, rotation, revocation, recovery and authenticated metadata together. It should also test whether a memory export can be corrected, attributed and imported without silently changing its provenance. Consent and understandable controls belong in the product behavior, while secret key material belongs in an appropriate protected store.

## Preserve human control and real approval boundaries

An agent's automatic execution setting does not make it the human approver for another system. The actual policy determines who may approve a request and what the approval covers. A prepared command must retain its target, effects, expiry, scope and identity through presentation and execution. A different participant may relay it, but that relay does not broaden its authority.

Fresh work should use fresh scoped requests. A consumed request should not be replayed to compensate for a timeout. When the result is unknown, the next step is a bounded reconciliation of the relevant effect. Retrying an uncertain mutation without that reconciliation can repeat the effect even when the first caller saw no success.

The proposed workflow treats useful persistence as reduction of uncertainty. It can try another supported read route when a tool is unavailable. It stops repeating the same unsupported operation when no new evidence would result. Numerical retry budgets are ceilings for appropriate attempts, not instructions to repeat an action regardless of its effect or failure mode.

## Research intake and scientific status

The current research continuation selects twenty primary papers or substantive reviews for comparison against a retained 22 November catalogue. Ten recur from that catalogue and ten are additions to the reading list. No selected item has been verified as published after that cutoff. An addition to a bibliography should not be reported as a newly published discovery.

The reading priorities include cosmological measurements, gravitational-wave constraints, laboratory tests, quantum-gravity effective theories and competing interpretations of gravity-mediated entanglement. For each entry, the working catalogue distinguishes journal publication, acceptance, preprint revision and commentary. A theoretical proposal is not an experimental detection; a published argument can be disputed without either side being ignored.

The current [Clay Millennium overview](https://www.claymath.org/millennium-problems/) lists Navier–Stokes as Active, Poincaré as Solved, and five other problems as Unsolved. [OpenAI's 8 September 2026 announcement](https://openai.com/index/navier-stokes-solution/) claims the forced-breakdown alternatives C and D with analytical and Lean artifacts. [Clay's 11 September statement](https://www.claymath.org/news/navier-stokes-announcement/) describes an apparent settlement while explaining its evaluation process. Those announcements, proof artifacts, independent proof checking and completed prize recognition are different claims.

The live [openai/math README](https://github.com/openai/math) reports 721 manuscripts in 373 families and approximately 42 percent of top-line results formalized. These are publisher-reported catalogue figures at this reading, not an independent enumeration or certification of every result. A remembered 722-item count has not been tied to a verified historical snapshot. The repository itself describes mixed verification stages and possible issues in unformalized material.

The GMUT research programme remains unvalidated. Its next useful scientific milestone is a restricted model with explicit fields or variables, dimensions, symmetries, conservation conditions, a validity regime, a known-theory limit and observable consequences. Changing an undefined coefficient or adding a suggestive term is insufficient. The model must identify a result that could count against it and avoid using the same data both to invent and to validate a prediction without accounting for that choice.

Ethical commitments and spiritual or philosophical interpretations can inform research priorities and governance. They do not replace physical measurements, mathematical proofs or operational security evidence. The THOS engineering programme likewise needs measured interface and failure-handling behavior before claims of a production operating system are appropriate.

## Review and validation boundary

This change is documentation only. It introduces no execution adapter, dependency, installation hook or permission change. The existing release payloads and their recorded evidence retain their previous versions. The new text should be reviewed for consistent evidence states, current source attribution and the absence of private operational data.

A repository check, when actually run, should report its exact commit and environment. It would validate the repository's stated checks at that revision; it would not execute the private ninety-item backlog, independently reproduce a research paper or validate GMUT. No such broader outcome is claimed by publishing this note.
